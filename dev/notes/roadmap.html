Where we are right now

The pipeline finished a multi-day cleanup sweep (Era 1) and shipped two new sibling packages (Era 2). The current focus is wiring those packages back into axon_recon for the first real end-to-end run (Era 3). Once that integration ships, four queued plans (Era 4–6) become unblocked.

An autonomous loop is currently executing slices through these eras; user input is reserved for the few hard gates flagged in plans.

Era 1 — Foundation cleanup

mostly shipped

The pipeline had accumulated legacy phases, duplicate config knobs, and a brittle force-restart contract. This era is a top-to-bottom cleanup: delete dead phases, rename ambiguous work for clarity, split off init + cleanup stages, standardize the parallelism story, and rebuild the auto-restart machinery so re-runs skip already-completed targets rather than blindly re-running.

  • shipped
    Phase roster cleanup
    14 slices, 12 shipped. Deletes 6 legacy phases, renames generate_gtrs → axon_velocity_gtrs, introduces init + cleanup stages, deletes --force-replot in favor of --replot, adds --output-root + in-progress checkpoint markers + target-level auto-restart skip across all four monolithic stage runners.
  • shipped
    Parallelism rationalization
    Collapsed nested resources.profiles, fixed n_jobs resolver fallback, retired max_plotting_concurrency, standardized log lines, migrated stale test fixtures, resolved 16 of 21 pre-existing test failures.
  • shipped
    Auto-restart machinery
    Checkpoint module + find_first_broken_phase + per-stage target_all_X_phases_succeeded helpers. Re-running an interrupted job skips finished targets instead of redoing work.
Implications

Runtime resume behavior is now robust — re-running an interrupted job doesn't redo finished work. The CLI flag surface is stable and documented. Test suite is much cleaner. The pipeline is navigable enough that integration and new-phase work can begin in earnest.

Era 2 — Sibling-package extraction

shipped

Two algorithm cores that previously lived inside axon_recon get extracted into standalone SpikeInterface-compliant Python packages. They sit alongside axon_recon, not inside it.

  • shipped
    kssynth — Kilosort sorter_output synthesizer
    Writes valid Kilosort folders (spike_clusters.npy, cluster_*.tsv, templates.npy, RawWaveforms) from arbitrary template + waveform sources. 58 tests. v1 feature-complete.
  • shipped
    unitlink — cross-session unit matching
    Wraps UnitMatchPy (with optional DeepUnitMatch v2 path) for matching units across recordings on the same chip. Two-halves shape, classical Naive Bayes spine, soft-import + mock-tested classical backend (now real-call after slice-5 redo). 53 tests.
Implications

Algorithms decoupled from pipeline plumbing → reusable outside axon_recon. SI-compliant interfaces mean other SpikeInterface users could adopt them. Both packages still local-only (no GH remotes) per the "validate before publishing" policy — push happens after the first successful end-to-end smoke through axon_recon.

Era 3 — Integration

in flight

Wire the new sibling packages back into axon_recon. The new abstractions start producing real results on real data here.

  • queued

    Recon stage uses kssynth to emit post-merge units as a SI-compliant sorter_output folder downstream consumers can read.
  • in flight

    Analysis-stage unitmatch phase invokes unitlink.match() once per (chip, well) group across DIVs. Slices 1–4 shipped (scaffold, group discovery, orchestrator, --targets chip-well:<chip>:<well>). Slice 5 enables the phase and runs the first login-node smoke.
Implications

This is the era's deliverable: the first end-to-end run of the new pipeline through real data, the first cross-session match tables, and the kickoff trigger for several queued plans (chip-layout, propagation-video, Radivojevic). Until this ships, the queued Era 4–6 plans wait.

⚑ Hard gate: slice 5 produces the first real-data match output for user review in memory/diagnostics_to_review.md.

Era 4 — Install + environment infrastructure

in flight (slice 1 done, 2–8 queued)

Today the install story is split across three artifacts that drift independently: environment.yml, the Dockerfile, and a referenced-but-never-written bootstrap script. Era 4 unifies it — pyproject.toml extras become the single source of truth for pip deps; environment.yml shrinks to conda-only; one flag-driven tools/setup_env.sh handles both production and editable-sibling install paths; the Dockerfile becomes shorter via pip install -e .[full]. Underpinned by a new env_parity guardrail that locks conda↔shifter capability parity.

  • in flight
    env_install_unification_plan (8 slices)
    Slice 1 audit done. Slices 2–8: migrate pip deps into pyproject extras, shrink environment.yml, write tools/install_dev_siblings.{sh,py} + tools/setup_env.sh with --editable-siblings flag, migrate Dockerfile to pip install -e .[full].
  • shipped
    env_parity guardrail
    Locks conda env ≡ shifter image capabilities, except Kilosort+CUDA stack and NERSC/HPC/SLURM plumbing (carve-outs). Any new conda dep mirrors into the relevant Dockerfile ARG (or surfaces a "rebuild needed" injection).
Implications

Contributors can clone + run one command to get a working dev env. Shifter rebuilds become reproducible from the same source of truth. Sibling editable installs become flag-toggled rather than separate manual steps. Timing constraint: should land before the next shifter rebuild — otherwise the rebuild reapplies the old per-sibling-ARG mechanism that slice 6 of this plan will throw away two weeks later.

Era 5 — Visualization & analysis enhancement

gated (post-Era 3)

Once unitlink match tables exist, visualizations can become globally aware of unit identity across sessions on the same chip. Two new plans capture this. Both gate on Era 3 shipping because they need real match tables for the color-consistency story.

  • gated
    chip_layout_phase_split_plan (8 slices, 2 user gates)
    Moves plot_full_chip_layout from recon stage to analysis stage AND splits into two phases: Phase A (white-bg multi-session timeline grid, color-coded reconstructions for tracking changes over time) + Phase B (black-bg detailed per-session with electrode overlay + signal-strength-weighted RGB blending where electrodes overlap). Cross-session color helper introduced in slice 3 is reused by the propagation-video work.
  • gated
    analysis_propagation_video_plan (9 slices, 1 hard-gate)
    Per-unit branch-propagation video / GIF generation via axon_velocity, as a new analysis-stage phase. Targeted on-demand (one video ≈ N minutes of compute, so opt-in via YAML + per-unit --targets triplet). Slice 1 does git archeology to surface an older recon-stage impl; fallback is clean wrap of axon_velocity's API.
Implications

Visual outputs become tools for tracking development over time on the same chip — same unit gets the same color across recordings. Per-unit deep-dive plots (with electrode-overlay color blending) become available. Timeline grids and propagation videos eventually serve as primary scientific outputs of repeated-recording experiments.

⚑ Hard gates: first real-data render of each new visualization requires user approval before downstream slices ship.

Era 6 — Alternative reconstruction algorithm (R&D)

gated (post-Era 3)

Re-implement Radivojevic et al. 2023's reconstruction algorithm as a sibling package + new recon-stage phase, with a side-by-side comparison phase in analysis. The published code reportedly isn't public, so the plan starts with exhaustive literature reading + a search for any GitHub / Zenodo / supplementary code before committing to a clean-room reimplementation.

  • gated
    radivojevic_recon_algo_plan (9 slices, 5 user gates)
    Sibling package at ~/dev/pkgs/radivojevic2023_recon_algo/ (user pre-populated literature/ with eLife 86512 + related papers). Slice 1 is research-only; slices 2–9 sequence behind user gate approvals. High back-and-forth plan — paper-identity confirmation, algorithm-summary review, input-compatibility decisions, real-data correctness review, attribution review.
Implications

Scientific comparison between two reconstruction approaches. Potentially uncovers shortcomings in the current axon_velocity-based pipeline. Attribution is explicit — package shipping requires citation + a DIVERGENCES.md documenting every place the implementation departs from the paper. If input requirements differ from axon_velocity_gtrs, additional plan injections may be needed for prerequisite phases in earlier stages.

⚑ Hard gate: first real-data Radivojevic output side-by-side vs axon_velocity_gtrs requires user approval before any downstream slices ship.
